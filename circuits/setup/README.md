# Trusted setup

Groth16 needs a per-circuit trusted setup: a public **phase 1** (Powers of Tau) and a
circuit-specific **phase 2**. Everything here is regenerated by `circuits/scripts/` and every
command below runs from the **repo root** (after `npm ci` at the root; circom 2.2.3 in
`~/.cargo/bin`, which the scripts put on `PATH`).

> **Status: DEMO-ONLY keys, not for production.** Phase 1 of both keys is the public PSE
> Perpetual Powers of Tau (contribution 0080, prepared for phase 2; since G2-S1-CIRC-040a).
>
> - **v4** (G2-S1-FINAL-001): phase 2 is a **simulated** 3-party ceremony. The three contributions
>   were made by separate AI agent processes on **one machine under one operator**, then closed by
>   the public drand mainnet beacon (round 6667474, announced in advance). Because one operator
>   controlled the machine, the multi-party trust guarantee does **not** hold: whoever ran it could
>   in principle have kept every contribution's randomness and forge proofs. The manifest says
>   `status: "DEMO-ONLY"`. Record: [`docs/ceremony/v4-ceremony-log.md`](../../docs/ceremony/v4-ceremony-log.md).
> - **v3**: phase 2 is **single-party**: **whoever ran setup could forge proofs**. The manifest
>   keeps `status: "DEV-ONLY"` with `status_detail` "DEMO-ONLY (single-party phase 2) ...".
>
> Fine for tests and the demo. For any real use, re-run the ceremony
> ([`../ceremony/README.md`](../ceremony/README.md)) with independent people each contributing on
> their own machine. See *Limitations*.

## One command

```sh
circuits/scripts/setup.sh <circuit.circom> <name>
circuits/scripts/setup.sh circuits/integrated_access_v3.circom integrated_access_v3   # v3 (G0)
```

That compiles at `--O2`, fetches or reuses a big enough phase-1 file, runs phase 2, verifies the
proving key (`ZKey Ok!`), exports the verification key and writes the manifest:

| File | Committed? | What |
|---|---|---|
| `circuits/setup/<name>.verification_key.json` | yes | the verifier's key (gateway, `verify.js`) |
| `circuits/setup/<name>.manifest.json` | yes | provenance: circom/snarkjs versions, r1cs/wasm/zkey/vkey sha256, ptau source + blake2b, constraint count, public-signal names in order, beacon, DEV-ONLY + single-party limitations, date |
| `build/<name>/<name>.{r1cs,sym,wasm,zkey}`, `verification_key.json` | no (build output) | compiled circuit and proving key of this run |
| `circuits/setup/<name>.{zkey,wasm}` | yes, for the pairs listed in [`ARTIFACTS.md`](ARTIFACTS.md) (decision D7) | the client's proving pair, copied by hand from `build/<name>/` |
| `~/zkp-cache/ptau/*.ptau` (+ `.info.json`) | no (outside the tree, ~36 MB at power 15) | cached phase-1 files, shared by every clone/worktree on the machine |

Then:

```sh
circuits/scripts/prove.sh  <name> <input.json> <outdir>                 # -> outdir/proof.json, outdir/public.json
circuits/scripts/verify.sh <name|vkey.json> <proof.json> <public.json>  # exit 0 valid, 1 invalid
circuits/scripts/artifacts.sh check   <name>   # committed pair == manifest, exported vkey == committed vkey
circuits/scripts/artifacts.sh install <name>   # check, then copy the pair to build/<name>/ for prove.sh
```

`prove.sh` reads `build/<name>/`; on a fresh clone run `artifacts.sh install <name>` first. Its
`input.json` holds **private** inputs (secret, salt, signature, Merkle path): keep it out of the
repo and delete it. The client should prove in-process (below) and write no input file at all.

Node consumers use `circuits/scripts/verify.js`: `await verify(vkey, publicSignals, proof)` returns
`true`/`false` and never throws. It rejects any public signal that is not a canonical decimal
(`isCanonicalSignal`: digits only, no leading zero except `"0"`, `< p`) because snarkjs alone
accepts `"0" + root` as the same value, and any proof coordinate that is not a canonical decimal
`< q`, a point at infinity, or a `pi_b` outside G2 (stock snarkjs accepts all three). Since
G1-S1-CIRC-037 it runs the fast verifier `circuits/scripts/fast-verify.js` (one verifier cached per
vkey content; ~5.6 ms warm vs ~14 ms for stock snarkjs, `circuits/reports/perf-v4.md`);
`ZKGATE_VERIFY_IMPL=snarkjs` selects stock snarkjs with the same input rules and point checks. It
checks the cryptography only; the gateway still applies the semantic checks of the
`access.public_signals` contract (`docs/CONTRACTS.md`): current root, and from v4 the pinned issuer
key, policy, `now`, nonce, epoch and nullifier (obligations 2-8). Call `terminate()` only when the
process is done (tests, CLI, shutdown): it releases the worker threads.

Overrides (environment): `BUILD_DIR` (default `build/`), `SETUP_OUT` (default `circuits/setup/`),
`PTAU_DIR` (default `~/zkp-cache/ptau`), `PTAU=<file>` to force a phase-1 file, `PTAU_POWER`,
`PTAU_SOURCE`, `PSE_PTAU_URL`, `PTAU_MIRRORS` (Hermez), `PTAU_FULL_VERIFY`, `BEACON_HASH`. The tests use temp dirs through them.

**Every run uses fresh randomness**, so re-running `setup.sh` gives a new zkey *and* a new vkey;
proofs made with the old zkey stop verifying under the new vkey. The re-key rule is in
[`ARTIFACTS.md`](ARTIFACTS.md).

## Phase 1: PSE ppot 0080 (Hermez is gone; dev is a fallback)

`circuits/scripts/ptau.sh` (`PTAU_POWER`, default 15 = 32k constraints; `setup.sh` raises it if a
circuit needs more). `PTAU_SOURCE=auto|pse|hermez|dev` (default `auto` = pse, then hermez, then
dev). Use `PTAU_SOURCE=pse` (what `npm run setup:v3|v4` set) so a missing file fails instead of
falling back to dev.

- **pse** (primary, since G2-S1-CIRC-040a): `ppot_0080_<NN>.ptau`, PSE's Perpetual Powers of Tau
  (the maintained successor of the Hermez files), prepared for phase 2 from contribution 0080 with a
  beacon (Ethereum beacon chain slot 7,325,000 `randao_reveal`, 31 iterations, per PSE's README).
  Reused from `PTAU_DIR` or downloaded from
  `https://pse-trusted-setup-ppot.s3.eu-central-1.amazonaws.com/pot28_0080/` and checked against
  the blake2b-512 pinned in `ptau.sh`; a mismatch (cached or downloaded) is fatal and never falls
  back. Only power 15 is pinned; other powers fail closed. The manifest records
  `"source": "pse-ppot-0080"` and a `provenance` string.
- **hermez** (kept, no longer downloadable): `powersOfTau28_hez_final_<NN>.ptau` (54 contributions
  plus a beacon), pins copied from the snarkjs README (`circuits/test/setup.test.js` cross-checks
  them). On 2026-11-08 the Google bucket and the hermez S3 bucket both returned AccessDenied at the
  source; the source stays for anyone holding a cached copy.
- **dev** (last fallback): reuses `pot<NN>_DEV-ONLY_final.ptau` from `PTAU_DIR` while its blake2b
  equals its `.info.json` sidecar; otherwise runs a local ceremony (`powersoftau new`, two
  contributions with `/dev/urandom` entropy on stdin, a beacon, `prepare phase2`, `verify`; ~10 min
  at power 15). The manifest records `"source": "dev"` and a DEV-ONLY phase 1 limitation.

## Phase 2

`groth16 setup` → **one** contribution (64 bytes of `/dev/urandom` fed to snarkjs's prompt on
stdin, never argv; snarkjs mixes in its own `crypto.randomBytes`) → a beacon (2^10 iterations; hash
from urandom, or `BEACON_HASH=<hex>` for public randomness fixed in advance) → `zkey verify`
against the r1cs and the ptau → export the vkey → manifest.

## Limitations

- **v3: single-party phase 2 — whoever ran setup could forge proofs.** We are the only contributor;
  replace via the multi-party ceremony (several independent contributors, then a public beacon)
  before any real use. Team action.
- **v4: simulated multi-party phase 2 — the operator of that machine could forge proofs.** The
  ceremony procedure ran in full (3 contributions, hashes published before each hand-off, every
  hand-off verified, a public drand beacon fixed in advance), but all three contributors were agents
  on one machine under one operator, so it gives no more trust than a single party. Re-run it with
  independent people on their own machines before any real use. Team action.
- **Phase 1 hash pinned on first download.** PSE publishes no blake2b for the prepared 0080 files
  and the full `powersoftau verify` was not run here (see the provenance table). A key built with
  `PTAU_SOURCE=dev` (or an unknown `PTAU=` file) gets a DEV-ONLY phase 1 limitation in its
  manifest; `ptau.source` says which phase 1 a key was built on.
- The beacon defaults to local randomness, so it is not publicly verifiable unless `BEACON_HASH`
  is set to a public value.

## Tests

`circuits/test/setup.test.js` (never re-runs setup; uses only the committed artefacts): manifest
provenance and DEV-ONLY/DEMO-ONLY/single-party records, the PSE ppot 0080 phase 1 (pin, provenance;
`ptau.sh` pse refuses a mismatched cache, an unpinned power and a failed download; manifest labels
per source), Hermez pins vs the snarkjs README, `artifacts.sh check`
passes and fails on a corrupted zkey or a vkey that is not the zkey's; a proof from the committed
pair for a TEST-ONLY input (built in memory from fixed seeds) verifies; a tampered root, a
leading-zero root, `root + p` and a tampered proof element do not; `verify()` never throws; the CLI
pipeline `artifacts.sh install` → `prove.sh` → `verify.sh` works in a temp dir (input file
deleted) and `prove.sh` refuses a policy-violating input. `SKIP_SETUP=1` skips the suite.

`circuits/test/setup_v4.test.js` (same rules, v4): manifest provenance (DEMO-ONLY, the 3
ceremony contributors in order, the public drand beacon, the committed transcript and its chain)
and the contract signal order, `artifacts.sh check|install` by name for v3 and v4, the `.gitignore` exemptions, a fresh
Alice -> Wiki proof (TEST-ONLY vector input, in memory) verifies with the expected 12 signals, each
of the 12 signals + 1 fails, leading-zero / `+ p` / swapped signals and the v3 key fail, and
`verify.sh integrated_access_v4` works. `circuits/test/fixtures_v4.test.js` and
`circuits/test/fast_verify.test.js` cover the fixtures and the verifier.
