# Report chapter: results for the P2 lane

Audience: the course and demo panel. This chapter compares what we measured with the targets in the
project scope ([`docs/project-scope.md`](../project-scope.md), "Evaluation"). The scope says its
targets are estimates and that we report whatever we measure.

## 1. Plain summary

On the machine below, a user's computer builds a proof in about one second and the gateway checks
it in about six milliseconds. The proof itself is 256 bytes as raw curve points. All three are
inside the scope's targets, with one honest exception: the stock snarkjs verifier alone is
slower than the 10 ms target, so the gateway uses a faster verifier that we wrote and tested. Two
things are not measured yet: proving inside a browser, and end-to-end latency against Keycloak,
which needs the gateway.

## 2. Measured numbers

Source for every row of this section: [`circuits/reports/perf-v4.md`](../../circuits/reports/perf-v4.md)
(raw samples in `circuits/reports/perf-v4.json`), generated by
`node circuits/scripts/perf-v4.js --prove-runs 60 --verify-runs 500 --warmup 20` on 2026-11-08.

**Machine.** Intel Xeon @ 2.10 GHz, 4 logical cores, 15.71 GB RAM, Linux 6.18.44, Node v22.23.4,
snarkjs 0.7.6. A shared sandbox host: peer agents may have been running (load average 0.42 before,
2.42 after), so the numbers are indicative, not a quiet-machine benchmark.

**Circuit.** `circuits/integrated_access_v4.circom`, depth 16, 9208 constraints (`--O2`), 12 public
signals, committed DEV-ONLY key.

| Series | Median | p95 | n |
|---|---:|---:|---:|
| Prove: `snarkjs.groth16.fullProve` (witness + proof), depth 16 | **941.89 ms** | 1063.76 ms | 60 |
| Verify, shipped `verify()` (fast), warm | **5.61 ms** | 7.59 ms | 500 |
| Verify, `ZKGATE_VERIFY_IMPL=snarkjs` (stock + point checks), warm | 15.48 ms | 20.18 ms | 500 |
| Verify, bare stock `snarkjs.groth16.verify` (reference), warm | 14.34 ms | 18.43 ms | 500 |

Cold first `verify()` in a fresh process (curve build and verifier precomputation): 273.8 ms.
"Warm" means a long-running gateway process, as in production.

### Against the scope targets

| Metric (scope) | Target | Measured | Result |
|---|---|---|---|
| Circuit size | report it; expect 10k to 40k | 9208 constraints at depth 16, `--O2` (4935 for v3) | reported; below the estimated range |
| Proving time, native (Node) | < 3 s | median 941.89 ms, p95 1063.76 ms | pass |
| Verify time at the gateway | < 10 ms | fast: median 5.61 ms, p95 7.59 ms | pass |
| Verify, stock snarkjs path | < 10 ms | median 15.48 ms, p95 20.18 ms | miss (kept only as an escape hatch) |
| Proof size | about 200 B | 256 B as raw points (A and C in G1: 64 B each; B in G2: 128 B); 723 B compact JSON, 806 B as committed | pass at the point level (128 B compressed); the JSON wire form is about 3x larger |

`perf-v4.md` judges pass or fail on p95. Verification cost depends on the number of public signals
(12), not on the constraint count, so it does not change with tree depth. Prove time does.

### Differences from the scope's method

- The scope asks for 100 runs, median and p95. The prove series has 60 runs, the verify series 500.
  The 100-run benchmark and the depth sweep (8, 16, 20) belong to `qa` (M8, `bench/`).
- Constraint counts for depth 8 and 20 are known (7264 and 10180 at `--O2`,
  [`circuits/README.md`](../../circuits/README.md)); their prove times are not measured.

## 4. What is still not measured

| Item | Why not | What closes it |
|---|---|---|
| In-browser proving (N1, scope target < 10 s) | N1 is a nice-to-have and is not built; all proving so far is native Node | N1 task, then `qa` benchmark |
| End-to-end request latency, ZK gateway vs Keycloak | needs the gateway (M5) and the Keycloak baseline (M7); neither is in this tree at these commits | `gateway`, `devops`, then `qa` M8 |
| Proving time vs Merkle depth (8, 16, 20) | benchmark mains exist; the sweep is `qa`'s | `bench/` |
| 100-run prove statistics | this report has 60 runs | `qa` M8 |
| Quiet-machine numbers | measured on a shared sandbox | rerun on an idle machine |
| Gateway denials end to end (replay, revoked, forged, expired, rate limit) | the circuit and fixtures are ready; the gateway is not | gateway implementation and `qa` e2e |
| Privacy comparison measured on the real gateway log | needs the gateway log | `safety` and `qa` |

## 5. Reading the results honestly

- The numbers show that the cryptography is cheap enough for per-request proofs. They do not show
  that the whole system is, because gateway work, network and the browser are missing.
- The keys are DEV-ONLY (single-party). Timings do not depend on that, but trust in the results of
  the security tests would, for a real deployment.
